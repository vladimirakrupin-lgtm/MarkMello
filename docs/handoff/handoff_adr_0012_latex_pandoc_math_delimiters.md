# Handoff: реализация ADR-0012 — LaTeX/Pandoc-разделители `\(...\)` / `\[...\]`

**Касается чего:** слой парсинга Markdown (`MarkMello.Infrastructure.Markdown`) — распознавание
математических разделителей Pandoc `\(...\)` / `\[...\]`; Presentation — нормализация `\boxed`.
**Источник решения:** `docs/adr/adr_0012_latex_pandoc_math_delimiters.md`.
**Статус:** реализовано в этой итерации (см. §3 — что сделано и почему именно так).

---

## 1. Решение ADR-0012 в двух словах

Разрыв — **не в движке отрисовки, а на слое парсинга**. `Sylinko.CSharpMath.Avalonia 12.0.0`
уже ест 16/18 формул файла-триггера. Markdig-математика знает только `$`/`$$`. Значит:

1. `\(...\)` → `MarkdownMathInline(IsDisplay: false)`;
2. `\[ ... \]` (разделители на своих строках, многострочное содержимое) → `MarkdownMathBlock`;
3. каноника ADR-0010 **расширена** (решение владельца): в текстовую карту и styled-text идёт TeX
   **с** Pandoc-разделителями — `\(...\)` / `\[\n…\n\]` рядом с `$...$`-формой, одна каноническая
   форма во всех слоях (иначе карта и styled-text расходятся по длине);
4. долларовые пути не трогаем — `MarkdownMathParsingTests` обязан остаться зелёным;
5. единственный реальный пробел движка в файле — `\boxed` (`:154`) — закрывается экспандером в
   `MarkdownMathTexNormalizer`; `equation`/`align` и `<caption>` — вне scope.

## 2. Подтверждённые факты (чтение кода + проба)

### 2.1 Markdig стирает бэкслэш — пост-AST слой невозможен

Пробный тест (временный, удалён) на `.UseAdvancedExtensions()`:

```text
Значение \(N_D\) и \(x\) тут.
→ LiteralInline => "(N_D"      // бэкслэша НЕТ, разбито на литералы
→ LiteralInline => ") и "
```

- Markdig трактует `\(`, `\)`, `\[`, `\]` как экранирование пунктуации → в AST приходит
  голый `(` / `)`. **По узлам Markdig отличить `\(x\)` от литерала `(x)` нельзя.**
- Внутри `CodeInline` содержимое сохраняется как есть; блочный math-контент (`$$...$$`)
  приходит как `MathBlock.Lines` с *флагом* начала строки.
- `$$...$$`, у которого открывающая часть не стоит в начале строки, математикой не
  распознаётся (проверено: `$${\n a\n}$$` → текст). Нативный display — `$$\n ... \n$$`
  или `$$ { ... } $$` в одной строке.

**Следствие:** конвертация — **пре-парсинг стадия над рабочей копией документа**, не
постобработка AST. `string.Replace` по всему документу и пост-AST — отклонённые варианты
(условие ADR: уважать code-контекст).

### 2.2 Формы замены (проверено на Markdig 1.1.2)

- `\(x\)` → `$x$`: **единственная** inline-форма, которую Markdig держит inline внутри пунктов
  списка и ячеек таблиц. `$$x$$` там рассыпается блок-парсером (список `- \(a\), b` распадался
  на `MathBlock(a)` + отдельный абзац). Требования `$`: содержимое не должно начинаться/кончаться
  пробелом — поэтому содержимое `Trim()`-ается.
- `\[` ... `\]` → `$$\n <тело> \n$$` — нативный display-блок; переходы строк внутри формулы
  сохраняются. После закрывающего `$$` добавлена **пустая строка**: Markdig иначе склеивает
  следующий абзац/таблицу как «ленивое продолжение» блока.
- `\[` в строке таблицы или в середине текста — это LaTeX-перевод строки, **не** display.
  Конвертер открывает display только в начале строки и вне строк-таблиц.

### 2.3 Прочие факты

- `MarkdigMarkdownDocumentRenderer.cs` — единственная точка разбора (`MarkdigMarkdown.Parse`).
- `TrySplitDisplayMathParagraph` (`.Math.cs`) уже промоутит одиночный `$$` в блок (пункты списка
  работают — проверено).
- `MarkdownMathTexNormalizer` — цепочка экспандеров; `MarkdownMathBinarySpacingExpander` идёт
  последним, поэтому `\boxed` обязан развернуться **до** него.
- `MarkdownMathSizedFractionExpander.TryReadGroup` — образец чтения `{...}` со вложенностью.
- **`\boxed` и `\fbox` и `\frame`** — движок не знает ни одного (`Invalid command`).
  `\overline`, `\underline`, `\overline{\underline{x}}` — валидны.
- Тесты парсинга живут в `tests/MarkMello.Presentation.Tests/` (проекта Infrastructure-тестов нет).

| Задача | Статус | Где |

### 3.1 Модули конвертера (NO GOD: ответственность разделена)

- `MarkdownLatexMathDelimiters.cs` — оркестратор `Prepare`: единый проход, сбор правок, `Apply`.
- `MarkdownLatexMathDelimiters.Inline.cs` — `\(...\)` → `$...$`, закрытие только на той же строке
  (висячий `\(` не съедает абзац); `\\)` не закрывает.
- `MarkdownLatexMathDelimiters.Display.cs` — `\[...\]` → `$$`-блок; закрывающий `\]` — первый токен
  своей строки; тело ищется построчно, code-строки пропускаются.
- `MarkdownLatexMathDelimiters.Scan.cs` — защита code: inline-span’ы (CommonMark «run of N»),
  fenced-блоки (``` / ~~~, ≥3), indented code, HTML-комментарии; `IsDisplayOpener` (начало строки,
  не строка-таблица).
- `MarkdownLatexMathDelimiters.Helpers.cs` — общие утилиты.

Все правки сохраняют строки прозы, поэтому `MarkdownSourceSpan` (номера строк) остаётся валидным
без перевода координат.

### 3.2 Перевод офсетов — не нужен

Офсеты источников не переводятся: span строится по номерам строк (`SourceSpans.cs`), а
конвертер не добавляет и не удаляет строк прозы (тело display сохраняет свои строки, `$$`-строки
занимают отдельную пару строк, но и в исходнике `\[` / `\]` были на своих строках). Проверено
тестом `DisplayDelimiterBecomesMathBlock` (`SourceSpan` непустой) и прогоном файла-триггера.

## 4. Отклонённые в ходе реализации варианты (и почему)

- `$$x$$` для инлайн-формул — рассыпается в списках/таблицах (см. §2.2).
- `$${ … }$$` одной строкой для display — не распознаётся как `MathBlock`.
- `\fbox` как аналог `\boxed` — движок тоже не знает.
- `Wrap макросом`/`\colorbox` — не поддерживаются; `\overline{\underline{}}` — единственный
  валидный «рамка сверху и снизу», сохраняющий содержимое и акцент.

## 5. Вне scope (по ADR)

- `\\(...\\)` (double-backslash, Pandoc `markdown_mmd`) — второй шаг.
- `<caption>` после таблицы (п.15) — отдельное решение (сейчас дропается generic-HTML, текст
  остаётся абзацем).
- `equation` / `align` (п.13a) — fallback ADR-0009 п.4.
