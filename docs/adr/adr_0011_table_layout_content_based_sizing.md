# ADR-0011: Table column sizing — content-based layout with degradation ladder and horizontal scroll

## Status

Утвержден

## Date

2026-11-18

## Related

- ADR-0009 — math formula rendering: формула рендерится как неразрывный
  фрагмент (`NoWrap`, `maxLines: 1`), измеряется по intrinsic-ширине.
  Это делает формулу «атомом» табличной вёрстки и прямо влияет на настоящее
  решение.
- Design baseline: `.mm-table` в MarkMelloDesign (`styles.css`) — модель
  border-collapse, паддинги ячеек, отступы таблицы.

## Context

Текущая реализация таблиц (`BuildTable` в
`src/MarkMello.Presentation/Views/MarkdownDocumentView.Tables.cs`) задаёт
все колонки одинаково: `GridLength(1, GridUnitType.Star)`. Ширина колонки
не зависит от содержимого. Текст ячеек переносится
(`TextWrapping="Wrap"` в `Controls.axaml`), но формула — нет
(`MarkdownMathTextRun`/`MarkdownMathMetrics`: `TextWrapping.NoWrap`,
`maxLines: 1`, замер с бесконечной шириной). При этом у `Border.mm-md-table`
стоит `ClipToBounds="False"`, поэтому переполнение не обрезается.

Следствия:

1. Колонки с коротким содержимым («да/нет», числа, единицы) занимают столько
   же ширины, сколько колонка со статьёй текста — место расходуется впустую,
   длинные ячейки получают неоправданно мало.
2. Длинная формула шире своей колонки (1/N ширины таблицы) и наезжает
   на соседние ячейки.

Требования владельца, зафиксированные в обсуждении:

- ширины колонок должны зависеть от содержимого;
- прежде чем показывать горизонтальный скролл — попробовать сжать таблицу:
  уменьшить шрифт до следующего стандартного размера и сократить пустое
  место между ячейками;
- если и это не помогло — горизонтальный скролл всей таблицы;
- при наведении на скрытые (обрезанные) данные — всплывающая подсказка.

## Decision

Пайплайн `BuildTable` становится четырёхступенчатым:
замер → content-based распределение → лестница деградации →
горизонтальный скролл с тултипами.

### 1. Замер min-content / max-content по ячейкам

Для каждой ячейки измеряются две ширины (подход CSS 2.2 §17.5.2.2):

- **max-content** — ширина контента в одну строку без переноса;
- **min-content** — минимальная ширина без переполнения: для текста —
  самое длинное слово (с учётом `LetterSpacing`), для формулы — вся её
  ширина из `MarkdownMathRenderer.Measure`, т.к. формула не разрывается.

Мерятся «пробные» `TextLayout` по тексту ячейки, а не живые контролы.
Замер кэшируется по ключу `(текст, fontSize, letterSpacing)`.

### 2. Content-based распределение ширин

Алгоритм в духе «auto table layout» браузеров:

1. Колонка, у которой max-content не превышает «честной доли» доступной
   ширины, получает max-content — короткие колонки больше не разбухают.
2. Оставшаяся ширина делится между «широкими» колонками пропорционально
   их избытку (max-content − min-content).
3. Каждой колонке гарантирован пол — её min-content.

Таблица по-прежнему растягивается на всю ширину контента документа
(`HorizontalAlignment.Stretch`); вертикальная компоновка строк не меняется.

### 3. Лестница деградации (до скролла)

Запускается **только** если сумма min-content колонок (с паддингами)
превышает доступную ширину — то есть переносом текста таблица уже не спасается.

На каждой ступени одновременно уменьшаются:

- шрифт ячеек: множитель от `ReadingPreferences.FontSize` —
  `0.92 → 0.85 → 0.80 → 0.75`, пол `12px` (консистентно с полом
  код-блоков и формул `Math.Max(12, …)`);
- паддинг ячейки: `14 → 8 → 4` (по горизонтали; вертикальный не трогаем).

Header и body деградируют синхронно. После каждого шага выполняется
перемер; первая ступень, на которой таблица помещается, — рабочая.

Деградация **локальна для конкретной таблицы** и не меняет пользовательскую
настройку `ReadingPreferences.FontSize`. Таблицы документа деградируют
независимо друг от друга.

### 4. Горизонтальный скролл — запасной сценарий

Если после минимальной ступени лестницы таблица не помещается:

- таблица оборачивается в `ScrollViewer` с
  `HorizontalScrollBarVisibility=Auto`, `VerticalScrollBarVisibility=Disabled`
  по образцу код-блоков (`BuildCodeBlock`), с резервом под скроллбар;
- ширина таблицы = сумма min-content колонок (скроллится вся таблица
  целиком, без сохранения content-based пропорций);
- колонкам задаётся ширина min-content; текстовым колонкам разрешено
  распределить излишек, если он есть;
- в скролл-режиме ячейки включают `ClipToBounds`: контент не наезжает
  на соседей;
- вертикальная прокрутка документа не перехватывается скроллером таблицы.

### 5. Тултип на скрытых данных

В скролл-режиме ячейка, чей контент шире колонки (прежде всего формулы),
получает `ToolTip` (по образцу `MarkdownImageView`):

- содержимое тултипа — **отрендеренная формула нормального размера**
  (контрол `ToolTip`, не текст LaTeX-источника);
- для обрезаемого текста дополнительно `TextTrimming="Ellipsis"`;
- тултип — ускоритель, а не единственный путь к данным: скрытое всегда
  доступно горизонтальным скроллом, выделение и копирование сохраняются.

### 6. Производительность и стабильность

- кэш замеров по `(текст, fontSize, letterSpacing)` в рамках
  `MarkdownDocumentView`; неизменённые таблицы не перемеряются
  (дифф блоков уже есть — `MarkdownBlockStructuralComparer`);
- гистерезис ширин при наборе текста: content-based ширины пересчитываются
  при изменении структуры/факта «помещается / не помещается», а не на каждое
  слово, чтобы колонки не «плясали»;
- при ресайзе окна/смене `ContentWidth` пайплайн перезапускается — таблица
  может «вернуть» деградацию при расширении.

### Отклонённые варианты

- **Сохранить равные `1*` колонки** — корень обеих проблем.
- **Чистый `table-layout: fixed` + ellipsis** — не решает проблему узких
  колонок и требует отдельного пути для формул.
- **Карточная вертикальная переупаковка строк** — меняет форму таблицы,
  для десктоп-ридера избыточно; возможно в будущем для узких окон.
- **Глобальная деградация шрифта для всех таблиц документа** — нарушает
  независимость таблиц и амортизирует настройку чтения.
- **LaTeX-источник в тултипе** — хуже для чтения; рендер формулы уже
  доступен и выбран.

## Consequences

Positive:

- ширины колонок соответствуют содержимому: короткие колонки узкие,
  длинные получают место;
- длинная формула больше не наезжает на соседние ячейки: сначала
  деградация, затем скролл, обрезка — только по границе ячейки;
- скрытые данные всегда достижимы и дублируются тултипом с рендером;
- деградация предсказуема: дискретные ступени, явный пол, независимость
  таблиц друг от друга.

Negative:

- появляется двухпроходный замер ячеек — дополнительная стоимость при
  rebuild; смягчается кэшем и гистерезисом;
- ширины колонок перестают быть тривиально предсказуемыми (равные доли) —
  визуальный результат зависит от содержимого;
- в скролл-режиме часть таблицы скрыта за прокруткой — компенсируется
  тултипами и видимым скроллбаром.

## Scope of changes

- Presentation:
  - `Views/MarkdownDocumentView.Tables.cs` — переработка `BuildTable`
    (пайплайн: замер → распределение → деградация → скролл/тултипы);
  - новый partial/модуль замера min/max-content (по правилам NO GOD FILES
    выносится из `Tables.cs`);
  - `Themes/Controls.axaml` — паддинги ячеек как настраиваемые классы
    ступеней деградации, стили тултипа;
  - константы лестницы (множители шрифта, паддинги, пол) — в одном месте.
- Домен и Infrastructure не меняются: замер работает поверх существующих
  `MarkdownTableBlock`/`MarkdownInline`, включая `MarkdownMathInline.Content`.

## Acceptance criteria

- Колонки с коротким содержимым уже, чем колонки с длинным текстом;
  ширины не равны «слепым» 1/N.
- Таблица с длинной формулой: сначала деградация шрифта/паддинга по
  ступеням, затем горизонтальный скролл; формула не перекрывает соседей
  ни на одной ступени.
- В скролл-режиме наведение на обрезанную формулу показывает тултип
  с отрендеренной формулой нормального размера.
- Две таблицы в одном документе деградируют независимо.
- При наборе текста в ячейке ширины колонок не «дрожат» от каждого слова.
- Сборка проходит, тесты на изменённый код зелёные; ручная проверка ридера
  на документе с таблицами (включая таблицы с формулами) пройдена владельцем.
